# 019 — 輸入錄放

狀態：**READY**
日期：2026-09-18
對應 issue：#14
前置：`docs/spec/003`（重播檔）、`docs/spec/006`（前端）、dosgolem `199-live-session-api`、`docs/re/004`（決定性）

---

## 1. 問題

現在要重現一段操作只有兩條路，都不好用：

- **手寫重播檔**（`docs/spec/003`）：按鍵時機要自己填指令數，適合固定的測試路線，不適合記錄「剛剛玩的那一段」。
- **xdotool 腳本**：以牆上時間送鍵，前端的轉場快慢會讓整串錯位（`docs/spec/017` §4 的實例：
  第 6 個 Return 之後畫面已經在迷宮）。

缺的是：**玩的時候把按鍵記下來，之後能一模一樣地放回去。**

## 2. 為什麼記「指令數」而不是時間

dosgolem 的決定性來自指令數（`docs/re/004`）：同一個狀態、同一串按鍵落在同樣的指令數上，
結果逐位元組相同。牆上時間不行——主機忙一點，同樣的 100 ms 會跑到不同的指令數。

這也是錄下來的檔案**換一台機器仍能重現**的原因。

## 3. 格式

```json
{
  "schema": "psychic-war-recording/1",
  "note": "說明",
  "pw_exe_sha256": "88321206…",
  "cycles": 750,
  "from": "states/07-first-play.state",
  "start_step": 138399466,
  "events": [
    {"step": 138401000, "key": "Up", "down": true},
    {"step": 138404300, "key": "Up", "down": false}
  ]
}
```

| 欄位 | 意義 |
|---|---|
| `pw_exe_sha256` | 錄製時的原版執行檔雜湊；不符就拒絕重播（換了執行檔，指令數對不上） |
| `cycles` | 錄製時的速度設定（`docs/spec/004`）；重播要用同一個值 |
| `from` | 從哪個狀態檔開始；空字串 ＝ 開機 |
| `start_step` | 錄製開始時的指令數（`from` 的狀態檔跑到這裡）；事件的 `step` 是絕對值 |
| `events` | 按下與放開各一筆，依 `step` 遞增。`key` 是 dosgolem 的具名鍵或單一字元 |

一個按鍵是**兩筆**事件（按下、放開），不是一筆帶長度：原版有些操作要按住，
長度資訊必須保留，而「按住多久」在錄製當下是未知的。

## 4. 怎麼錄、怎麼放

- **錄**：前端 `-record <檔案>`。每次送 `KeyDown`／`KeyUp` 時記一筆（鍵名、當下的指令數）。
  熱鍵（F1／F2／F3／F5／F6／F10／F11）不記——它們是前端自己的功能，不進遊戲。
- **放**：`tools/replay_record.py` 把錄製檔轉成 probe 的 `-hold` 參數
  （`<鍵>@<起點>+<長度>`，dosgolem `197`），再由 probe 以指令數排程送出。
  用 `-hold` 不用 `-press`：後者走 FIFO 佇列且會節流，排得太密的鍵會被延後（`docs/spec/003` §3）。

## 5. 驗收

1. **錄一段再放一次，狀態逐位元組相同**：從同一個狀態檔起跑，錄一段含移動與戰鬥的操作，
   重播之後的觀測變數（`lin:16966` 起 52 bytes）與錄製結束時相同。
2. 反向對照：把錄製檔裡某一筆事件的 `step` 改掉（例如 ±50 萬），重播結果**不同**——
   證明這個比對真的看得到差異，不是「兩邊都沒動」。
3. 執行檔雜湊不符時拒絕重播並說明原因。
4. 錄製時不記熱鍵：錄製過程按 F10，錄出來的檔案裡沒有 F10。

## 6. 之後

錄製器記的是「指令數 ＋ 鍵」，與遊戲無關，穩定之後抽回 dosgolem（`CLAUDE.md` 的分層原則：
換一款遊戲還成立的就往上游送）。格式裡的 `pw_exe_sha256` 到時候改成通用的欄位名。
