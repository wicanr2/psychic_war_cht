## 2. 量測細節

### 2.1 節拍與 CPU

`psychicwar -load-state 07-first-play.state -audio null -stats … -quit-after 61s`（容器 2 核、Xvfb 軟體 OpenGL）：

| 指標 | 值 |
|---|---:|
| 第 1–61 秒牆上時間 | 60,013 ms |
| 同期機器時間 | 60,013 ms |
| 同期計時器刻 | 4,321（72.001 Hz） |
| 第 1 秒放棄追趕 | 397 ms（第一次繪圖；之後 0） |
| 欠載（第 1 秒後） | 0 |
| CPU／牆上時間 | 1.86 核（主要是 Xvfb 的軟體 OpenGL） |

dosgolem 改成 IRQ0 絕對排程後，在主機 load average 約 21（其他使用者的工作）時重量：牆上 60,007 ms、機器 58,854 ms（−1.92%）、
72.009 Hz、1.40 核、放棄追趕 1,152 ms、欠載 136。計時器頻率仍在 ±1% 內；時間差來自 CPU 被搶（實際只拿到 1.40 核，前一次需要 1.86 核），
不是排程。**前端需要約 2 個空閒核心**（Xvfb 軟體 OpenGL 下）；上表 0.000% 是主機較空時的結果。

計時起點原本在建立視窗之前，第一秒會算成落後 355 ms、欠載 40 次；改成第一次 `Update` 才起算後，第 1 秒放棄追趕仍有約 400 ms（推定是第一次繪圖編譯 shader），之後穩定。

### 2.2 鍵盤實測（`tools/frontend-playthrough.sh`）

- 每一步先等畫面與重播檢查點相符（縮回 320×200 後不同像素 ≤ 容許值）再送鍵：`02-match`、`04-cleared`、`05-select`、`06-name`、`07-first-play` 都是 0 像素；
  `03-protection` 對不上（差 151 像素），因為防拷題目依亂數出，按鍵時機不同就出不同的戰士與基地名稱。
- 名字 kai、前進 6 步遇 Shulosu（38）、按住空白鍵 35 秒 → 敵人消失，玩家 40 → 29、能量 12（dosgolem `756bf1f`，IRQ0 絕對排程）。
  損血每次實跑都可能不同：按鍵時機與計時器相位都會改變單場結果（`docs/re/010` §4.5）。
- 戰鬥後按 Left：方位 North → West；按 Esc：出現「What do you want to do?」與 Ask Kayla／See Items／ESP Power／Options／Cancel 選單
  （`workplace/fe/play/turn.png`、`esc.png`）。
- 實測時腳本每 0.5 秒截圖與前端搶 CPU，`dropped_ms` 9 秒、欠載 962 次；節拍與欠載以 §2.1 為準。

### 2.3 音訊內容：前端送出的取樣與 DOSBox-X 比

欠載次數只說明「有沒有斷」，不說明「對不對」。前端加 `-wav`，把每次 `Render()` 的取樣原樣另存（44,100 Hz 單聲道），
從開機錄 95 秒標題音樂，用 `tools/music_compare.py audio` 比（判準見 `docs/spec/001`）：

| 對象 | 配對 | 頻率誤差最大 | 斜率 | 起點殘差 p95／最大 | 判定 |
|---|---:|---:|---:|---:|---|
| DOSBox-X（`workplace/dosboxx-audio/title.wav`） | 628／628（100%） | 0.31% | 1.00007 | 6.9／13.7 ms | 通過 |
| dosgolem 離線合成（`-dump-tone-wav`） | 630／630（100%） | 0.83% | 1.00002 | 6.0／11.2 ms | 通過 |

修到通過前經過兩個 dosgolem 的問題（都在分支 `psychic-war/r4-live`）：

1. **事件以步數定位**：前端落後時一次補跑 100 ms，而字串指令讓步數與 cycles 不成比例，音符起點偏幾十毫秒。
   改成以寫入當下的 cycles 定位（規格 `199-live-session-api` §3.5）。
2. **IRQ0 相對排程**：修完 1 仍只配對 20.8%。按音高序列逐段對齊後，前端與離線合成的偏移在前 376 段從 −9.59 秒漂到 −10.59 秒，
   之後固定；同一個音符前端長 10–20%。音符長度以計時器刻數計，所以是**計時器在繪圖多的標題動畫期間變慢**：
   一整道 `rep movsb` 在一步裡扣掉幾萬個 cycles，「送出當下 ＋ 間隔」每次晚到、累積。改成絕對排程（規格 `198-dosbox-cycles` §3.2）後通過。

⚠ §2.1 的 72 Hz 是在迷宮裡量的（繪圖少），看不出問題 2；**計時器頻率要在繪圖密集的畫面量**。

### 2.4 AdLib 路徑（`-adlib`）

從開機錄 95 秒標題音樂（`-adlib -audio null -wav`），用 `docs/spec/002` 的方法對樂譜比（`tools/music_compare.py opl`，樂譜是 dosgolem 暫存器紀錄）：

| 對象 | 起音命中 | 音高在場（523 個音） | 起音殘差 p95 |
|---|---:|---:|---:|
| 前端即時合成 | 67.6% | 48.8% | 33.9 ms |
| dosgolem 離線合成（`docs/re/007`） | 59.8% | 49.3% | — |
| DOSBox-X 錄音 | 65.4% | 39.6% | 31.8 ms |

- 前端與離線合成落在同一水準；這個方法本身分不出合成器的好壞（`docs/re/007` §4），判準仍是「不通過」，所以**不能**拿它當 AdLib 正確的證據。
  AdLib 的正確性以事件層為準（`docs/re/012`：暫存器序列與 DOSBox-X 逐筆相同）。
- 同一次：牆上 94,020 ms、機器 84,222 ms、欠載 1,065 次、放棄追趕 9,799 ms、1.17 核。量測時主機 load average 約 30（其他使用者的工作），
  前端拿不到 2 核；**AdLib 路徑 60 秒不斷音沒有量到有效數字**，要在主機空閒時重量。

## 3. 找到的限制（寫成規則）

- **按鍵要跨過一次輪詢**：Ebiten 每 1/60 秒看一次按鍵狀態。`xdotool key` 的按下與放開只差幾毫秒，兩次輪詢之間就結束，前端收不到。
  自動化送鍵一律「按下 → 0.15 秒 → 放開」。真人按鍵通常超過 1/60 秒，但極快的連點可能漏掉（推定，未量測）。
- **轉場期間送的鍵會被吃掉**：750 cycles 下畫面轉場比 DOSBox-X 8000 cycles 慢得多；「畫面一變就送下一鍵」會把轉場當成按鍵有反應。
  自動化要等目標畫面出現（檢查點比對），不能只等畫面變化或靜止（選單箭頭會閃）。
- **null 音訊輸出要用 `time.Now()`**：CPU 被搶時 ticker 的時間戳可能早於上一次，算出負的取樣數（實測 panic）。

## 4. 限制與重開條件

- 只驗 Linux（docker＋Xvfb，軟體 OpenGL）；實機 GPU、Windows、macOS 未驗（#35）。
- `-audio ebiten` 在容器裡沒有音效卡，未實際發聲；即時發聲要在有音效卡的機器上驗。取樣內容已驗（§2.3），剩音效卡端的延遲與斷音。
- AdLib（`-adlib`）路徑：取樣內容與離線合成同一水準（§2.4）；60 秒欠載要在主機空閒時重量。
