# 037：怎麼知道「現在在戰鬥中」

狀態：量測紀錄（2026-09-19）。對應 issue #40（遊戲內可調執行速度）。規格 `docs/spec/023`。

## 1. 結論

**用執行位址判斷，不用記憶體值判斷。**

| 事件 | 執行期位址 | IDA | 是什麼 |
|---|---|---|---|
| 戰鬥開始 | `0161:47D4` | `14CE4` | 戰鬥主迴圈 `sub_14CE4` 的進入點 |
| 戰鬥結束 | `0161:47AD` | `14CBD` | `call sub_14CE4` 的**下一道指令** |

這兩點**剛好把戰鬥主迴圈包起來**，而戰鬥的難度就是那個迴圈（`docs/re/010` §3：敵我雙方
每圈各判定一次，迴圈不讀計時器）。打贏與用 F3 逃走兩種出口都會走到 `0161:47AD`，
各只觸發一次（§4）。

讀狀態檔（F11 即時讀檔、`-load-state`）時這兩個掛鉤都不會觸發，所以另外補一條：
**載入之後由敵人 HP 字組 `0x509C` 重推**（不為 0 就當成戰鬥中）。這一條會把「逃走後殘留
的 38」誤判成戰鬥中，一路維持原速到下一場戰鬥結束為止。誤判方向是慢，不會讓戰鬥變快（§5）。

## 2. 原本的候選訊號為什麼不能用

### 2.1 敵人 HP 字組 `0x509C` 單獨用會卡住

19 個檢查點裡只有 `08-encounter`（戰鬥中）是 `0x26`＝38，其餘 18 個都是 0
（`workplace/states/*.state` 逐一 `-peek lin:509C:2`）。看起來可以當旗標。

但**用 F3 逃離戰鬥時，這個字組不會被清掉**：

```
tools：probe -load-state 08-encounter.state -cycles 750 -steps 92000000 \
       -press 3D -press-at 86500000 -watch 509C-509D
結果：整段 0 筆寫入（敵人 HP 一直是 38）
畫面：第 88,200,000 步回到迷宮（方位由北變南，與 docs/re/036 §4 相同）
```

所以逃走之後 `0x509C` 永遠停在 38，直到下一場戰鬥覆蓋它。只靠這個值會**永久停在
「戰鬥中」**。而下一場如果遇到同一種敵人（HP 也是 38），值一樣沒變，輪詢看不出換了一場——
那一場就會跑在加速檔位上。這是會改變難度的方向，不能接受。

### 2.2 觀測變數 52 bytes 裡沒有戰鬥旗標

`0x16966` 起的 52 bytes（`docs/re/011`）逐一比過 `07-first-play`／`08-encounter`／
`09-battle-won`／`12-battle2`／`19-zellwal`，戰鬥狀態與迷宮狀態的差異只在座標。

戰鬥**結束**時確實有一批腳本變數被寫（`0161:3CA2` 起的 `sub_141B2`，把戰鬥結果搬進
`0x1697A`–`0x1698D`），打贏與逃走都會寫。但那些值**不會在戰鬥開始時清成 0**：
第二場戰鬥結束時 `0x1697A` 是 `01 → 02`，不是 `00 → 02`。所以「`0x1697A` 不為 0」
不能當「戰鬥結束」，「`0x1697A` 變了」也不可靠——結果碼會重複（19 段裡出現過 1、1、2、2）。

`0x16996` 是戰鬥次數（0→1→2→3→4 隨場次遞增），但**逃走不計數**（F3 那一段沒有寫入），
同樣不能當出口。

### 2.3 畫面內容不行

戰鬥時操作面板（ADVANCE／LOOK ASIDE／TURN／OPERATION）仍然在畫面上，面板在不在
分不出戰鬥與迷宮。標題、防拷、選單、輸入名字同樣沒有面板，拿面板判斷會把整段開場
也算成戰鬥。

## 3. 程式結構（靜態，解釋為什麼掛在這兩點）

位元組碼直譯器的兩個處理常式（`workplace/ida/PW_UNP.EXE.asm`，IDA `14CA7` 與 `14CB7`，
兩段都不在 IDA 認出來的函式裡）：

```
; IDA 14CA7（只佈置敵人、不打）
        call    sub_14038      ; 戰鬥佈置（寫敵人 HP 到 cs:3A8C ＝ 線性 0x509C）
        call    sub_141B2      ; 把結果搬進腳本變數
        call    sub_16770 ×2
        mov     bx, 2
        retn
; IDA 14CB7（真的打）
        call    sub_14038      ; 戰鬥佈置
        call    sub_14CE4      ; ← 戰鬥主迴圈（IDA 14CBA 呼叫，返回位址 14CBD ＝ 0161:47AD）
        call    sub_14421 / sub_143C2 / sub_1449E / sub_14542 / sub_144B8 / sub_145E1   ; 結算
        call    sub_141B2      ; 把結果搬進腳本變數
        call    sub_16770 ×3
        mov     al, cs:byte_1356D+0A53h
        mov     ah, 0
        mov     bx, ax
        retn
```

兩個處理常式都呼叫 `sub_14038`（會寫敵人 HP），**只有後者呼叫戰鬥主迴圈**。
掛在 `sub_14CE4` 的進入點與返回點，就不會被前者干擾。

敵人 HP 的寫入指令在 IDA `14108`（`2e891e8c3a  mov word ptr cs:[3A8Ch], bx`）。
⚠ probe `-watch` 報的 `ip=0161:3BFD` 是**下一道指令**的位址（`OpAddr()` 在寫入完成後取），
不是寫入指令本身。查反組譯時要往回一道。

## 4. 時序量測（750 cycles／毫秒，`08-encounter` 之前那一場）

方法：`probe -regs-at 0161:47D4,0161:47AD,0161:3CA2`（執行到就記暫存器）配
`-watch 509C-509D`（記憶體寫入）與 `-shots`（每 5 萬～10 萬步存一格畫面，
再用 `tools/frames.py summary` 與 `08-encounter.frame`／`07-first-play.frame` 逐像素比）。
原始輸出在 `workplace/battle-detect/`。

### 4.1 戰鬥開始

從 `07-first-play`（第 42,000,000 步）依重播送 8 次 Up，第 6 步遭遇：

| 步數 | 事件 | 與戰鬥迴圈進入點的距離 |
|---:|---|---:|
| ~83,030,000 | 畫面開始由迷宮換成戰鬥（解析度 5 萬步）| −186,000 |
| 83,200,000 | 畫面已經和 `08-encounter` 只差 413 像素（99.4% 畫完）| −16,000 |
| 83,216,183 | 敵人 HP `0x509C` 由 `00` 寫成 `26`（IDA `14108`）| −90 |
| **83,216,273** | **戰鬥主迴圈 `0161:47D4` 進入**（只 1 次）| **0** |
| 83,400,000 | 畫面與 `08-encounter` **逐像素差 0** | +183,727（≈ 0.24 秒）|

**換檔的時點落在「戰鬥畫面已經畫好、戰鬥迴圈還沒跑第一圈」之間。**
轉場那 0.25 秒的繪圖跑在玩家選的檔位上，戰鬥本身一圈都不會。

### 4.2 戰鬥結束（打贏）

從 `08-encounter`（第 86,000,000 步），第 86,500,000 步起按住空白鍵：

| 步數 | 事件 | 與戰鬥迴圈返回點的距離 |
|---:|---|---:|
| 96,054,938 | 敵人 HP 寫成 0（IDA `14A70` 附近，玩家攻擊）| −56,160 |
| **96,111,098** | **戰鬥主迴圈返回 `0161:47AD`**（只 1 次）| **0** |
| 96,252,637 | `sub_141B2`（`0161:3CA2`）把結果搬進腳本變數 | +141,539 |
| 96,300,000 | 敵人圖像已擦掉，畫面靜止（非零像素 26,192，之後 1,100,000 步雜湊不變）| +188,902 |
| ~97,800,000 | 迷宮畫面回來（與 `09-battle-won` 差 47 像素）| +1,688,902（≈ 2.25 秒）|

第二場（`10-saved` → Kasuruji，敵人 HP 70）同樣的形狀：HP 歸零 258,301,312、
結果搬移 258,547,766、迷宮畫面約 260,750,000（返回點之後約 2.9 秒）。

**戰鬥迴圈返回之後還有 2.2～2.9 秒才回到迷宮，這段會跑在玩家選的檔位上。**
那段畫面是靜止的（敵人已經擦掉、沒有文字），量到的非零像素數與雜湊在 110 萬步內完全不變，
所以加速只會讓這個停頓變短，看不到「動作變快」的跳動。這是刻意接受的邊界，不是疏忽。

### 4.3 戰鬥結束（F3 逃走）

從 `08-encounter`，第 86,500,000 步送掃描碼 `3D`（F3）：

| 步數 | 事件 |
|---:|---|
| **86,569,849** | **戰鬥主迴圈返回 `0161:47AD`**（只 1 次）|
| 86,571,058 | `sub_141B2`（`0161:3CA2`）搬結果 |
| 87,269,852 | 朝向 `0x16970` 由 0 改成 2（向後一步）|
| ~88,200,000 | 迷宮畫面回來（返回點之後約 2.17 秒）|
| 全程 | 敵人 HP `0x509C` **一次都沒有被寫**，停在 38 |

## 5. 邊界與沒驗到的

- **讀狀態檔沒有掛鉤訊號。** F11 即時讀檔與 `-load-state` 之後改由 `0x509C != 0` 重推。
  存檔點在戰鬥中 → 正確；在迷宮中 → `0x509C` 是 0（18 個檢查點都驗過）→ 正確；
  在「逃走之後」存的檔 → 誤判成戰鬥中，一路維持原速到下一場戰鬥的 `0161:47AD` 為止。
  誤判方向是**慢**，不會讓戰鬥變快。要縮短這段，得另外加一個「位置變了就解除」的條件；
  目前沒加，因為它會讓判斷多一個來源，而症狀只是「該快的時候沒快」。
- **玩家陣亡沒有驗過。** 陣亡一樣要從 `sub_14CE4` 返回才會回到腳本，所以 `0161:47AD`
  應該同樣觸發；沒有做出陣亡的狀態檔來驗。推論等級：**假說**。
  即使不觸發，殘留狀態是「一直原速」，方向安全。
- **只驗過兩場戰鬥**（Samar 的 Shulosu 與 Kasuruji）與一次 F3 逃走。
  多人戰鬥、投降、Turbogun（F1）結束的戰鬥沒有驗過。
  這三種都走同一個 `sub_14CE4`，所以推論它們同樣成立；推論等級：**強證據**（靜態結構）。
- **位址是這一版 `PW.EXE` 專屬的**，而且是 EXEPACK 解壓後在 dosgolem 上的執行期段值
  `0161`。換執行器或換版本都要重新確認。前端已經用同一個段值掛了 9 個印字掛鉤
  （`apps/psychicwar/translator`），這裡沿用同一套。
- `-watch-screen` 在這幾次量測上**一行都沒印**（`-screen-delta 2000`、取樣每 2 萬步）。
  沒有回頭查為什麼；畫面時序改用 `-shots` ＋ `tools/frames.py summary` ＋ 對參照格
  逐像素比，這條路走得通就沒再追。**這是一個沒解釋的空結果，不要拿它當「畫面沒變」的證據。**

## 6. 驗收數字（前端實跑，`docs/spec/023` §8）

`tools/frontend-speed-check.sh 1 3`，Xvfb 裡跑真正的前端，原速 750 cycles、檔位 1× 與 3×。

### 6.1 不按任何鍵跑 20 秒（決定性，沒有輸入抖動）

| 起點 | 檔位 | 機器秒 | 跑到的指令數 | 機器÷牆上 |
|---|---:|---:|---:|---:|
| `07-first-play`（迷宮）| 1 | 19.91 | 56,929,642 | 0.99 |
| `07-first-play`（迷宮）| 3 | 52.80 | 81,596,429 | 2.64 |
| `08-encounter`（戰鬥中）| 1 | 19.90 | 100,924,633 | 0.99 |
| `08-encounter`（戰鬥中）| 3 | 19.85 | 100,889,840 | 0.99 |

戰鬥中兩個檔位跑到的指令數差 **34,793 步（0.034%）**，機器÷牆上都是 0.99。
迷宮裡 3 倍檔跑到 2.64 倍（上限是算繪，見 §6.4）。

### 6.2 走路（按住 Up 走 5 格）

| 檔位 | 5 格總秒數 | 每格秒 |
|---:|---:|---:|
| 1 | 1.58 | 0.316 |
| 3 | 0.60 | 0.119 |

每格 0.316 → 0.119 秒（2.66 倍）。0.316 秒與 `docs/re/010` §4.3 的「≤ 0.27 秒」相容
（那邊量的是「畫面畫完」，這邊量的是「下一格的變數寫進去」，多了一次按鍵重複的等待）。

### 6.3 戰鬥（從 `08-encounter` 按住空白鍵打完）

| 檔位 | 戰鬥結束的指令數 | 結束時的牆上毫秒 | 戰鬥區間機器÷牆上 |
|---:|---:|---:|---:|
| 1 | 103,945,892 | 24,052 | 0.995 |
| 3 | 103,945,892 | 24,037 | 0.995 |

**指令數完全相同**，牆上毫秒差 15 ms（0.06%）。同一組量測在稍早一輪也是
同一個指令數（24,061 / 24,067 毫秒），兩輪之間相同。

⚠ 指令數相同是加分不是判準：xdotool 的按鍵落在哪一個指令數有抖動，而計時器中斷的相位
會讓同一場戰鬥差到 ±30%（`docs/re/010` §4.5）。這兩次剛好相同，是因為整段都以原速節拍跑，
牆上時間到指令數的對應一致。判準是「戰鬥區間的機器÷牆上 ＝ 1.00」。

### 6.4 量測條件與偏差方向

容器 `--cpus 3`，Xvfb 軟體算繪，`-audio null`、`-text off`。
CPU 用量**兩個檔位都是**每 20 秒約 55 秒（約 2.8 核），
**瓶頸是算繪不是模擬**——所以 3 倍檔只到 2.64 倍，前端放棄了 7,212 毫秒的虛擬時間
（`Pacer.DroppedMs`）。這個偏差的方向是「加速幅度看起來比較小」，
通過就算數（同 `docs/re/010` §4.6 的規則）。真機有 GPU 時算繪成本接近零，會更接近 3.00。

音訊（環形緩衝）八次執行都是欠載 29–37 次、溢位 0，與檔位無關。
⚠ 音訊額度改成看牆上時間之前（照檔位固定抽 1/n），同一個 `idle-maze` 3 倍檔量到
**欠載 295 次**——因為機器其實只跑到 2.6 倍，照 3 抽會把聽得到的聲音抽掉。
`docs/spec/023` §5 的「抽多少看牆上時間不看檔位」就是這個量測逼出來的。

### 6.5 反向對照

`tools/frontend-hotkeys-check.sh`（原速，沒有 `-speed`）全部通過：
F5 英文模式 vs 原版畫面、F5 切回中文、F4 開關、F11 讀檔、F11 拒絕讀，**不同像素都是 0**；
F4 說明頁（已加上 F12 那一行）與由 `text/help.json` 算出的期望值差 0 / 576,000，
內容底緣 y=595／600；讀檔前後的觀測變數相同。原速時畫面上不畫常駐標記（實跑截圖確認）。

## 7. 重現

```sh
# 戰鬥開始（掛鉤觸發的步數）
probe -load-state 07-first-play.state -cycles 750 -steps 86000000 \
      -press up,up,up,up,up,up,up,up -press-at 43000000 -press-every 4000000 \
      -regs-at 0161:47D4,0161:47AD,0161:3CA2 -regs-max 8
# 戰鬥結束（打贏）
probe -load-state 08-encounter.state -cycles 750 -steps 100000000 \
      -hold "space@86500000+30000000" -regs-at 0161:47D4,0161:47AD,0161:3CA2
# 戰鬥結束（F3 逃走）
probe -load-state 08-encounter.state -cycles 750 -steps 92000000 \
      -press 3D -press-at 86500000 -regs-at 0161:47D4,0161:47AD,0161:3CA2
```

（`probe` ＝ `tools/battle-pace.sh` 裡那一段 `worktrees/dosgolem/tools/go.sh run ./cmd/probe`
的包裝，含 `-exe /orig/psychic-war/PW.EXE -root /orig/psychic-war`。）
